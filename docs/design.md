# 设计说明

> 依据：`docs/decision-log.md`（B1–B6）与 `docs/备料助手-一页纸需求清单.md`（v1.0）。
> 本文只讲结构与约束，不重复需求。

## 1. 定位

备料段的协同系统：拥有自有账本（建议单 / 交接待办 / 留痕），在**两级授权**下可回写执行结果字段。它不是全公司的记录系统，也不接管采购下单。

## 2. 分层

| 层 | 职责 | 关键约束 |
|---|---|---|
| 接入层 | 三个只读源（ERP / 订货平台 / 生产台账）+ 写目标 | 每源一个 adapter，统一内部模型；只读源 15 分钟刷新 |
| 主数据层 | 品类 / 批次 / 门店码表 + 映射 | 未映射不出建议；字典版本只增不改 |
| 规则层 | 换算、短保判定、六要素校验 | **确定性规则，禁止模型**；每条建议可指回字典版本 |
| 确认层 | 采用 / 微调 / 改判，交接确认 | 只追加不覆盖；确认需具名；时间取服务端 |
| 回写层 | outbox + 幂等键 + 版本校验 | 本地成立、异步送达；冲突必转人工 |
| 观察层 | 健康巡检、历史回放、指标 | 完整率是准入闸门，不降级放行 |

依赖方向单向向下，规则层不得反向依赖接入层（否则无法回放）。

## 3. 三条关键路径

**早班主路径**
`拉取订货单 → 匹配批次与字典 → 生成建议 → 班组长确认 → 本地成立 → 投递 outbox`

**回写路径**
`确认 → 入 outbox（幂等键）→ 投递目标系统 → 成功则标记已同步 / 版本冲突则冻结该行并进裁决队列`
失败不回滚现场确认，只影响同步徽章。

**降级路径**
`接入失败 → 沿用带时间戳的只读快照 → 顶栏标「暂未更新」→ 可确认、动作进本地队列 → 恢复后按业务编号去重提交`

## 4. 部署形态

私有化内网部署，配方与出成率不出企业边界；无外部大模型调用。端侧只缓存只读快照与提交队列，**规则引擎不下沉**（防字典版本漂移）。

## 5. 技术选型

尚未在评审中锁定。`requirements.txt` 中的 FastAPI / SQLAlchemy 为建议基线，写实施计划时确认；选型不得违反第 2 节约束。

## 6. 与外部系统的契约

- 读：需要品类 / 批次 / 门店编码、数量、状态、事件时间；缺字段走健康巡检而非静默补零
- 写：需要幂等键语义、版本号或 ETag、明确的拒绝原因码；否则无法实现「冲突转人工」
- 时间：外部事件时间与本地写入时间分别记录，不做时区假设
